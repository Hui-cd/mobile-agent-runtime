# Android Agent 产品与交互设计

> 状态：Draft
> 范围：运行在 Android 手机上的 Agent v0
> 原型：[`prototype/android-agent`](../prototype/android-agent/README.md)

## 1. 产品定义

Android Agent 让用户用自然语言把一个手机任务交出去，并在必要时重新取得控制权。

它不是远程控制器，也不是把每次点击都展示给用户的聊天机器人。用户关心的是：

1. Agent 是否正确理解了目标；
2. 它现在在做什么；
3. 哪些动作需要自己决定；
4. 最终是否真的完成。

v0 只覆盖只读或低风险的跨应用任务。支付、购买、发送、删除等外部副作用必须单独确认。

## 2. 交互契约

```text
用户提出目标
  → Agent 明确理解与执行边界
  → Agent 自主执行
  → 风险或阻塞时把控制权交还用户
  → 用设备观察证据报告结果
```

交互遵守五条约束：

- 用户表达目标，不需要学习 Tool、Intent 或 Accessibility；
- 系统展示可理解的动作语义，不展示原始 Tool Call；
- 低风险且含义明确的任务不增加多余确认；
- 有外部副作用、关键歧义或需要用户操作时必须暂停；
- 没有执行后的设备证据，不宣称任务完成。

## 3. 控制权

| 阶段 | 控制者 | 用户需要知道什么 |
|---|---|---|
| 输入任务 | 用户 | 能做什么、当前是否具备执行条件 |
| 理解任务 | Agent；必要时用户确认 | 目标、范围和重要假设 |
| 执行 | Agent | 当前动作、目标应用、可以停止 |
| 风险确认 | 用户 | 操作对象、具体动作、可能后果 |
| 异常恢复 | 用户或 Agent | 阻塞原因、已保存进度、如何继续 |
| 完成 | 用户 | 实际结果、证据和未完成部分 |

## 4. 关键流程

### 4.1 正常流程

```text
任务输入 → 理解任务 → 执行 → 观察验证 → 结果
```

“理解任务”不一定是独立页面。只有目标存在重要歧义、执行范围较大或会切换多个应用时，才要求用户确认；简单、只读、可逆的任务可以直接执行，同时用一句话显示 Agent 的理解。

### 4.2 风险操作

```text
执行 → 暂停 → 展示对象、动作和后果 → 用户允许/拒绝
                                      ├─ 允许 → 执行并验证
                                      └─ 拒绝 → 跳过或结束
```

确认内容必须来自结构化动作语义，不能只显示“是否允许继续”。例如：

```text
发送给：微信联系人张三
内容：我大约 10 分钟后到
影响：发送后对方立即可见
```

### 4.3 需要用户处理

```text
执行 → 登录失效/验证码/权限缺失 → 保存进度 → 用户处理 → 明确恢复
```

Agent 不盲目重试，也不把“去登录”算作任务结束。用户回来后应看到原任务、已完成步骤和“继续执行”。

### 4.4 停止

用户在运行和等待确认时都可以停止。停止后进入明确终态，并说明是否已经产生外部影响；不自动重放未确认状态的动作。

## 5. 页面与状态

| 状态 | 必须展示 | 主要操作 |
|---|---|---|
| 首次配置 | 模型连接、设备控制权限及用途 | 保存配置、前往系统设置 |
| 任务输入 | 输入框、可执行状态 | 开始任务 |
| 理解任务 | 目标、范围、关键假设 | 开始、修改 |
| 执行中 | 当前应用、当前动作、阶段性进度 | 返回 Agent、停止 |
| 风险确认 | 对象、动作、后果 | 允许、拒绝 |
| 等待用户 | 原因、已保存进度、恢复条件 | 去处理、继续、结束 |
| 完成 | 结果、设备证据、实际影响和未完成项 | 返回、再次执行 |
| 失败/停止 | 原因、已经发生的动作 | 重试安全步骤、结束 |

首次配置属于 onboarding，不进入日常任务主流程。配置完成后，仅在连接或权限失效时重新出现。

## 6. Tool Call 如何映射到界面

| Runtime 事件 | 用户界面表达 |
|---|---|
| `device_observe` | 正在确认当前页面 |
| `device_invoke(open_app)` | 正在打开“时钟” |
| `device_act(click)` | 正在选择“闹钟” |
| Policy 要求审批 | 暂停并展示风险确认 |
| Tool 返回可恢复阻塞 | 展示原因、保存进度并等待用户 |
| ToolResult 含 Observation | 更新进度或形成完成证据 |

UI 使用业务语义；原始参数、调用 ID、JSON 和错误堆栈只进入诊断记录。

当前 Android 实现已经建立可见性基线：任务运行前明确说明界面操作会打开目标 App；执行通知是开始任务的前提；运行通知持续显示当前步骤并提供停止入口；等待确认使用高优先级通知引导用户返回 Agent；完成、失败和停止都会留下可点击的终态通知。当前结论为源码实现并通过本地构建与状态映射单测，尚未完成真机交互验证。

## 7. 状态模型

```text
IDLE
  → REVIEWING
  → EXECUTING
      ├─ WAITING_APPROVAL → EXECUTING
      ├─ WAITING_USER_ACTION → EXECUTING
      ├─ CANCELLED
      └─ FAILED
  → COMPLETED
```

每次任务只能有一个终态。`COMPLETED` 必须由最终回答和成功 ToolResult 证据共同支持。

## 8. 当前实现差距

| 目标设计 | 当前实现 | 后续收口 |
|---|---|---|
| 结构化风险确认 | `ApprovalRequest` 只有描述文本，风险主要由关键词判断 | 引入动作、对象、后果和风险等级 |
| 等待用户处理后恢复 | 目前只有审批等待 | 增加 `WAITING_USER_ACTION` 与恢复上下文 |
| 停止是独立终态 | Android 已增加 `CANCELLED` 与终态通知 | 真机验证，并记录停止前已产生的影响 |
| 完成结果带结构化证据 | 当前主要展示模型最终文本 | 绑定完成声明与最后的 Observation/审计记录 |
| 任务范围确认 | 当前提交后直接运行 | 按歧义和风险决定内联说明或确认页 |

这些差距是目标设计，不表示当前版本已实现。

## 9. 验收标准

- 用户无需理解技术术语即可发起任务；
- 执行前，用户能够判断 Agent 理解的目标是否正确；
- 执行中，用户能够知道当前动作并随时停止；
- 风险确认能够回答“对谁、做什么、有什么后果”；
- 登录、验证码和权限阻塞不会触发无限重试；
- 任务恢复不会重复可能已经产生副作用的动作；
- 完成结果包含可观察证据，并明确未完成或无法验证的部分；
- 首次配置完成后不干扰日常任务。
